# The ADR domain model

Owns: the ADR record, its lifecycle map, the DACI roles and their permission verdicts, history, discussion (comments and issues), tags,
successors, search, saved filters (lenses), expiry, notifications, the Markdown export and the decision log (overview) — the sketch, refined per version as each part is built. Not here: the user's decisions and the roadmap
(`product.md`), list conventions (`list-endpoints.md`), migration and locking rules (`persistence.md`), guard ordering (`authorization.md`).

Read before touching `adrs/` (server) or any ADR page (web).

## The record (`adrs`, 0.2.0 — built)

| Field | Wire | Rule |
|---|---|---|
| id | `id` (int32) | the row key (`SERIAL`, like every table of the foundation: `EventLog`, `lockActiveForWrite` and the typed routes are `UInt`-keyed; the first sketch said UUID); URLs use it |
| number | `number` → shown as `ADR-0042` (`key`) | one global gapless counter, `MAX(number)+1` over every row under `pg_advisory_xact_lock` (Adder's `ThreadService` thread number, made global; `persistence.md` "ADRs (V10)"); never reused, a cancelled or soft-deleted ADR keeps its number; the key pads to four digits and grows beyond 9999 |
| name | `name` | 1–120 chars, single line; unique among non-deleted ADRs, case- and accent-insensitive (`uq_adrs_name_active`, a clash is `409`); omitted or blank at create = the problem's first non-blank line cut to 120 (a clash of the defaulted name is `409` too, the creator names it); a PUT needs a name |
| problem/question | `problem` | required, Markdown, ≤ 20 000 chars |
| context | `context` | Markdown, ≤ 20 000; required to enter `IN_REVIEW` |
| decision | `decision` | Markdown, ≤ 20 000; required to enter `IN_REVIEW` |
| alternatives considered | `alternatives` | Markdown, ≤ 20 000; optional |
| accepted consequences / side effects | `consequences` | Markdown, ≤ 20 000; required to enter `IN_REVIEW` |
| status | `status` | the lifecycle below |
| tags | `tags` `[{name, retired}]` | the ADR's tags from the registry ("Tags" below), alphabetical; set by `PUT /adrs/{id}/tags`, never by the document PUT |
| predecessor / successor | `supersedes` / `supersededBy` `{id, key, name, status}` + `supersedesAccepted` / `supersededByAccepted` | the successor link ("Successors" below); `supersedes_id` lives on the successor and is set by `PUT /adrs/{id}/supersedes`; `supersedes_accepted_id` (V19) records the predecessor's Approver's acceptance |
| expiry date | `expiresOn` (`YYYY-MM-DD`, nullable) | the LAST day the decision is in force: the sweep expires an `ACTIVE` ADR whose date is before today (UTC), i.e. the day after. A CHANGED date must not be in the past (any non-terminal status); entering `ACTIVE` with a date already past is `400` (the sweep would expire it at once). **Whose it is:** until the decision is in force the Driver, the Approver or ADMIN; once `ACTIVE` only the Approver or ADMIN (the Driver could otherwise end a decision in force by dating it to today; 1.0.0, `canEditExpiry`), and a changed or removed date of an `ACTIVE` ADR is a notice to its participants (`EXPIRY_CHANGED`, "Notifications") |
| revision | `revision` + `X-Expected-Revision` | optimistic concurrency on the document PUT, the transitions, the participants PUT and (0.4.0) the tags and supersedes PUTs (Adder/Toadie `infra/revision`, header required on all five); starts at 1, every real change and every sweep move bumps it, a no-op bumps nothing |
| audit | `createdAt`, `createdById`, `updatedAt`, `statusChangedAt` | epoch millis like every sibling |

The text fields are stored as sanitised (`sanitizeSingleLine` for the name, `sanitizeMultiLine` for the Markdown: CRLF to LF, control and hidden direction characters `400`, leading blank lines and trailing whitespace dropped); the optional ones are empty strings, never null. `problem` is required at create and on every PUT; the others default to empty. A create may carry all the content fields at once (a problem that arrives with its solution).

## Lifecycle (`AdrLifecycle.kt`, Covenant's `contracts/Lifecycle.kt` shape)

```
PROBLEM_RAISED ──► SOLUTION_DRAFT ──► IN_REVIEW ──► ACTIVE ──► EXPIRED     (sweep, expiresOn passed)
      │                  │ ▲             │ │            ├──────► SUPERSEDED  (automatic, successor activated)
      │                  │ └─────────────┘ │ send back  └──────► WITHDRAWN   (the decision is revoked, 0.7.0)
      └──────────────────┴───────────────┼─┴─► CANCELLED
                                         └───► WITHDRAWN
```

`PROBLEM_RAISED → IN_REVIEW` is allowed too (a problem that arrives with its solution skips the draft). **Send back and withdraw (0.7.0):** `IN_REVIEW → SOLUTION_DRAFT` returns an ADR to drafting (content, participants and tags are kept and nothing is cleared; the Approver has to review it again once the next `→ IN_REVIEW`, which re-validates the required fields, sends it back to review) and `ACTIVE → WITHDRAWN` revokes a decision in force (terminal like every ending: read-only, its open issues and escalations stay resolvable as on an `EXPIRED` one, its expiry-reminder marker is never read again because the pass looks at `ACTIVE` ADRs only). **A reason** rides any transition (`{to, reason?}`): free text of at most 1000 code points (`sanitizedTransitionReason`: CRLF to LF, control and hidden direction characters `400`, both ends trimmed, blank = none, judged after the stale revision), stored as `TRANSITIONED` `reason`, shown by the history, and never in a notice, an email or an audit line (the audit says `reasoned`). **Consequences:** a successor that is still pre-active when its predecessor is withdrawn keeps its link but cannot be activated (`400`, "unlink it first", as for an expired predecessor; the predecessor is terminal so its owners cannot detach, the successor's Driver removes the link; since 1.2.0 the successor's Driver and Approver are TOLD when the predecessor is cancelled, withdrawn or expires, and the ended ADR stops listing the successor, "Successors"); a SUPERSEDED predecessor whose successor is later withdrawn stays `SUPERSEDED` (nothing is resurrected) and still points at it (`successorInPlayOrInEffect`: a withdrawn successor counts as the replacement when it carries `SUCCESSOR_ACTIVATED`, one withdrawn before it activated never does). An illegal move is `409` of the
typed problem `urn:hammurabi:problem:illegal-transition`; a move whose target requirements fail is `400` naming the missing fields.
**The picture (1.1.0):** the detail page's Lifecycle tab draws this map with who takes each move, the ADR's own status and the moves the caller may make now (`web/CLAUDE.md` "The lifecycle diagram"). `EXPIRED` and `SUPERSEDED` are never requested by a user: the system moves into them, and a user asking for either gets the same `409`
(ADMIN included). Terminal: `CANCELLED`, `WITHDRAWN`, `EXPIRED`, `SUPERSEDED` — a terminal ADR is read-only (every write is the typed `409`
`urn:hammurabi:problem:adr-frozen`; ADMIN may still soft-delete it).

**Requirements** (`missingForTransition`): entering `IN_REVIEW` needs `context`, `decision`, `consequences` and an Approver (the name and the
problem exist from creation, alternatives stay optional); entering `ACTIVE` re-checks the same (content and participants stay editable in review, so
an Approver may have left) plus a date already set not in the past. The `400` names every missing field in its detail.

**Content freeze** (`requireContentEditable`): name and the five Markdown fields change only in `PROBLEM_RAISED`, `SOLUTION_DRAFT` and
`IN_REVIEW`; once `ACTIVE` a content change is `409 adr-frozen`, while the expiry date (the Approver's or ADMIN's from then on), the participants and the tags stay editable. A sent-back ADR is back in drafting, as pre-active as it was in review. The successor link is the
opposite: it is set only while the ADR is pre-active (a link on an `ACTIVE` ADR is `409 adr-frozen`), because it takes effect at activation.

**Order inside a write** (`authorization.md`). Before all of it, the per-user `adr-write` bucket (1.2.0: `429`, 120 a minute across the 13 writes, before the ADR is looked up). The body's own SHAPE checks of the document, participants and tags PUTs (the 400s that need no table) run BEFORE the lock, right after the coarse role and the header; everything else is judged under the row lock, in this order:
- document PUT: the coarse role (403), the header and the body's shape (400: name, lengths) before the lock, then under it a terminal ADR (409 `adr-frozen`), the **stale revision (409 `revision-conflict`)**, then per field the content freeze (409 `adr-frozen`) or the role (403: the content Driver, Contributor, ADMIN; the expiry date Driver, Approver, ADMIN, and once `ACTIVE` only Approver, ADMIN) and a past expiry date (400) — the revision comes before the per-field judgements, so a stale save is never a false 403 (and never writes a false `authz.denied`) or 400;
- transition: the coarse role (403), the per-move role (403), the lifecycle map (409 `illegal-transition` — also a move out of a terminal status, and a request for `EXPIRED`/`SUPERSEDED`), the stale revision (409), then the `reason` (400) and the target's requirements (400);
- participants: the coarse role (403), the header (400), **no self-approval (403)**, **the set's shape (400: exactly one Driver, at most one Approver, each person once, the size cap), judged BEFORE the lock** (the self-approval ban needs only the body, so it comes first: a malformed set from a caller naming themselves Approver is still `403`), then under the lock the guard again, a terminal ADR (409 `adr-frozen`), the stale revision (409), **who holds the Approver seat (403: once the ADR has been in review only the current Approver or ADMIN changes it), judged against the locked participants** (it waits for the revision so a stale editor that did not touch the seat gets the `409`, never a false `403`), and last the users (400: unknown or inactive, which needs the table);
- tags (0.4.0): the coarse role (403), the header (400), **the names' shape (400: malformed, duplicate, over 20), judged BEFORE the lock**, then under the lock a terminal ADR (409 `adr-frozen`), the stale revision (409) and the registry (400: unknown or retired name);
- supersedes (0.4.0): the coarse role (403), a terminal ADR (409 `adr-frozen`), the stale revision (409), an `ACTIVE` ADR (409 `adr-frozen`), then the predecessor (400: itself, unknown or deleted, terminal; 409: closes a cycle, already has a successor in play);
- detach successor (`DELETE /adrs/{id}/successor`): judged on the PREDECESSOR - the coarse role (403), optional `successorId` query validation (400), a terminal predecessor (409 `adr-frozen`), then no matching pending successor (404);
- accept successor (1.0.0, `POST /adrs/{id}/successor/accept` `{successorId}`, no header): judged on the PREDECESSOR - the standing (404), the coarse role (403: Approver, ADMIN), the body (400), then under the locks a terminal predecessor (409 `adr-frozen`), a predecessor not `ACTIVE` yet (409), a pending successor other than `successorId` (404), already accepted (204, nothing written);
- the activation also needs the ADR it replaces to be `ACTIVE` (below), judged with the other requirements (400), and - over an `ACTIVE` one - its Approver's acceptance: **409 `successor-not-accepted`, after the stale revision and before the reason and the requirements**, ADMIN included.

A save that changes nothing is `204`, bumps nothing and records nothing.

## DACI roles and verdicts (`AdrAccess.kt`)

Participants live in `adr_participants` (adr, user, role, added at/by). Exactly one `DRIVER` (always present — the creator at first) and at
most one `APPROVER` (required to enter `IN_REVIEW`); any number of `CONTRIBUTOR` and `INFORMED`; one role per user per ADR.

| Action | Who |
|---|---|
| read, list, history, discussion; comment or ask (pre-active), raise an issue or an escalation (active) | any authenticated user |
| create | any authenticated user (becomes the Driver) |
| edit content (pre-active states) | Driver, Contributors, ADMIN |
| `PROBLEM_RAISED → SOLUTION_DRAFT`, `→ IN_REVIEW`, `→ CANCELLED` | Driver, ADMIN |
| `→ ACTIVE`, `→ WITHDRAWN` (from `IN_REVIEW` or `ACTIVE`, 0.7.0) | Approver, ADMIN |
| send back (`IN_REVIEW → SOLUTION_DRAFT`, 0.7.0) | Approver (returns it for rework), Driver (pulls it back), ADMIN |
| change participants, tags, successor | Driver, Approver, ADMIN (the Driver role can be handed over, never left empty); the successor link is the SUCCESSOR's (the predecessor's roles do not matter) and only while it is pre-active |
| change the expiry date | Driver, Approver, ADMIN while the ADR is not in force; **once `ACTIVE` the Approver or ADMIN only** (1.0.0: the Approver decides, so the Driver cannot end a decision in force); a terminal ADR, nobody |
| make oneself the Approver | ADMIN only (0.7.0: nobody else, at any status; a participants PUT that names the caller Approver is `403` unless they already are) |
| add, remove or replace the Approver | until the ADR has first been in review the Driver, the Approver, ADMIN; **from then on (`IN_REVIEW`, `ACTIVE`, and a draft again after a send back) only the CURRENT Approver or ADMIN** (0.7.0) |
| accept a pending successor (1.0.0) | the Approver or ADMIN of the PREDECESSOR (a decision in force only; the Driver cannot, nor can the successor's Approver) |
| detach a pending successor | Driver, Approver, ADMIN of the PREDECESSOR, while it is non-terminal and the successor is still pre-active (the answer to a link parked by a stranger; below) |
| curate the tag registry (categories and their tags) | ADMIN only; any authenticated user reads it |
| resolve or reopen an issue / escalation | Driver, Approver, ADMIN |
| answer or reopen a question | its author, Driver, Approver, ADMIN |
| edit a discussion entry | its author only |
| delete a discussion entry (a tombstone) | its author, ADMIN |
| soft-delete | ADMIN only |

Guards run before validation: a forbidden write is `403` even when its body is also invalid (`authorization.md`). A missing ADR is `404`.
The verdict is also computed FOR THE CALLER and served on the ADR: `allowedTransitions` (the map minus the system's moves, filtered by the table
above), `canEditContent` (the content in a pre-active status: the Driver, a Contributor, ADMIN), `canEditExpiry` (the date: see the table), `canManageParticipants`, `canChangeApprover` (0.7.0: the Approver seat is the caller's to change), `canEditTags` (a non-terminal ADR), `canEditSuccessor` (a pre-active one) and `canDetachSuccessor` (this ADR is the PREDECESSOR of a pending successor and the caller holds one of the three roles on it) and `canAcceptSuccessor` (this ADR is `ACTIVE`, its pending successor is not accepted yet and the caller is its Approver or ADMIN), so the SPA never re-derives it.
The coarse guard before the body is "may touch this ADR at all" (edit: Driver, Contributor, Approver, ADMIN; transition, participants, tags and supersedes: Driver,
Approver, ADMIN); the per-target and per-field rows above are re-judged under the row lock (`403`).

**Participants** (`PUT /adrs/{id}/participants`, a wholesale replace applied as a diff, under `X-Expected-Revision` — REQUIRED like the document PUT, so a stale editor cannot silently drop people another one added; a real change bumps the ADR revision, a no-op bumps nothing): exactly one Driver in the set (the creator at first),
at most one Approver, each user once, at most 100, every user NEW to the set (or taking a new role) an active account. One event per added, removed
and changed participant; a set that changes nothing is `204` and records nothing. Creation takes optional extra participants (never a Driver, never
the caller; one `PARTICIPANT_ADDED` each).

**Who holds the Approver seat (0.7.0, the review of the withdraw).** The Approver decides (activates, withdraws), so the seat is protected from the people it decides over: (a) a non-ADMIN caller can **never assign the Approver role to themselves**, at any status (no self-approval; `403` unless they already hold it, so an Approver's own PUT that keeps them is fine); (b) once the ADR has **ever been in review** (it is `IN_REVIEW` or `ACTIVE`, or a draft again after a send back, or terminal) only the **current Approver or ADMIN** may change who holds it (add, remove or replace that row; the Approver may hand it on or leave it empty; if their account was deleted, ADMIN fixes it). "Ever" closes the send-back bypass (the Driver sends an ADR in review back, swaps the Approver in the draft, resubmits and the accomplice activates it): the Driver keeps the send back to fix the text, not the seat. It is read from the history (a `TRANSITIONED` event into `IN_REVIEW`, `AdrEventService.hasEnteredReview`, no flag or migration; a `PROBLEM_RAISED` ADR cannot have been, `IN_REVIEW` and `ACTIVE` always have, so only a draft or a terminal ADR queries). A participants PUT that leaves the Approver row as it is stays open to the Driver, a Driver handover included, and until the first review the Driver may still name, replace or drop someone else as Approver. Without it the Driver could, in two requests, put themselves in the seat (handing the Driver seat to a friend) and then approve or withdraw their own ADR. Both rules are judged under the row lock against the locked set (`requireNotSelfApproval`, then after the terminal and revision checks `requireMayChangeApproverSeat`); the SPA's picker is disabled when `canChangeApprover` is false and never offers the caller (an ADMIN excepted). Audit: the generic `authz.denied`.

## History (`adr_events`, 0.2.0)

Lettuce's/Adder's `EventLog` machinery: one immutable structural event per mutation, committed in the same transaction as the write.
Types and their string `params` (the SPA renders them in the viewer's language; no rendered text is stored): `CREATED` `{key, name}` (the actor is the
Driver), `UPDATED` `{changed: "name,context,…", <field>.from?, <field>.to?}` (field-level: the Markdown fields — problem, context, decision,
alternatives, consequences — by NAME only, the short ones `name` and `expiresOn` with their sides, an absent side meaning unset; Toadie's
`FieldChange` vocabulary, one event per save), `TRANSITIONED` `{from, to, reason?}` (0.7.0: the optional free-text reason), `PARTICIPANT_ADDED` / `PARTICIPANT_REMOVED` `{userId, name, role}`,
`PARTICIPANT_CHANGED` `{userId, name, from, to}`, `EXPIRED` `{expiresOn}` (system actor), and from 0.4.0 `TAGS_CHANGED` `{added?, removed?}` (comma-joined tag names, each key only when non-empty), `SUCCESSOR_LINKED` / `SUCCESSOR_UNLINKED` `{predecessorId, key, name}` (on the successor; a detach also writes `SUCCESSOR_UNLINKED` `{successorId, key, name}` on the PREDECESSOR), `SUPERSEDED` `{successorId, key, name}` (on the superseded predecessor, actor = the user who activated the successor) and `SUCCESSOR_ACTIVATED` `{predecessorId, key, name}` (on the successor, same transaction), `SUCCESSOR_ACCEPTED` (1.0.0: `{predecessorId, key, name}` on the successor and `{successorId, key, name}` on the predecessor, the actor is who accepted), `PREDECESSOR_ENDED` (1.2.0: `{predecessorId, key, name, status}` on a pending SUCCESSOR when the ADR it was set to replace was cancelled, withdrawn or expired, `status` being the predecessor's new one; the actor is who ended it, NULL for the expiry sweep),
the discussion's eight (0.3.0, below: `COMMENTED`, `QUESTION_ASKED`, `QUESTION_ANSWERED`, `QUESTION_REOPENED`, `ISSUE_RAISED`, `ESCALATED`, `ISSUE_RESOLVED`, `ISSUE_REOPENED`). A no-op save records nothing, and so does a refused write. The
actor is the acting user (on the wire `actorId`, `actorName`, `actorDeleted`; the stored `EventLogRow` keeps `userId`/`userName`/`userDeleted`), or NULL for a system event. Read through `GET /api/v1/adrs/{id}/events` (paged,
newest first by default, sortable by `id` and `createdAt`; any authenticated user). A soft delete is audit-only (the ADR is gone from every read).

## Expiry (`AdrExpirySweep.kt`, 0.2.0)

A periodic loop on the background scope (Covenant's `ReleaseLineReminders` shape; `adrs.expiry.enabled` / `adrs.expiry.intervalSeconds`, env
`ADRS_EXPIRY_*`, boot-validated) sweeps at start and then every interval: it moves every `ACTIVE` ADR whose `expires_on` is before today (UTC; the
date is the last day in force) to `EXPIRED`, each in its own transaction (the revision bumps) with a system-actor event and the `adr.expired` audit.
Idempotent and safe on several replicas (the candidate scan is only a filter; each ADR is re-read under its row lock with the status and date
predicate). "Today" is an injected `Clock`, so tests expire deterministically (`AdrExpirySweepTest`); the suite itself runs no loop.

## Discussion (`adr_discussion`, 0.3.0 — built)

`adrs/AdrDiscussion*.kt`, V12; Covenant's `version_reviews` ported and reshaped (its open/outdated/closed review and approvals are gone: an ADR has ONE open thread, an entry has a kind and a state). One table, one service
(`AdrDiscussionService`), the pure verdicts in `AdrDiscussionAccess.kt`. An open decision log: **any authenticated user reads and posts**.

| Kind | Accepted while the ADR is | State | Settled by |
|---|---|---|---|
| `COMMENT` | `PROBLEM_RAISED`, `SOLUTION_DRAFT`, `IN_REVIEW` | none | - |
| `QUESTION` | the same | `OPEN` → `ANSWERED` (and back) | its author, the Driver, the Approver, ADMIN |
| `ISSUE`, `ESCALATION` | `ACTIVE` | `OPEN` → `RESOLVED` (and back), an optional `resolution` note (≤ 2 000) | the Driver, the Approver, ADMIN |

- **The window** (`DiscussionKind.acceptedIn`) is judged under the ADR row lock (`FOR NO KEY UPDATE`, like every ADR write), so a post can never slip in after a lifecycle move; outside it a post or an edit is the typed `409` `urn:hammurabi:problem:discussion-closed`. The
  **state change** (answer, resolve, reopen) and the **delete** are open in EVERY status: an issue on an ADR that later expired or was superseded can still be settled, a question answered after activation, and the moderation path is never closed. Reads are open in every status: **entries stay readable forever**.
  A discussion write never bumps the ADR `revision`. Each entry carries its own revision (V22), starting at 1. Editing, changing state
  or a resolution note, and deleting increment it on a real change. Edits, state changes and deletes accept the entry's
  `X-Expected-Revision` and return a typed `409 revision-conflict` for a stale value under the ADR row lock, even if the requested
  change would be a no-op. The SPA sends the revision it acted on. For v1 compatibility a write without the header uses last-write-wins.
- **The entry.** Markdown `body` 1–10 000 characters (`sanitizeMultiLine`; blank, too long or a control character is `400`), the author (`authorId`, `authorName`, `authorDeleted`, flat like every person on the wire), `createdAt`, `editedAt` (the author's edit; the same text writes nothing), `state` (stored in the column `status`; the enum is `DiscussionState`, values unchanged, so no data migration), `resolution`,
  `stateChangedById`/`stateChangedByName`/`stateChangedByDeleted` and `stateChangedAt`. A **soft delete leaves a tombstone**: `deleted` true, `body`, `state`, `resolution`, `editedAt`, `stateChangedById`/`stateChangedByName` and `stateChangedAt` null on the wire (`stateChangedByDeleted` false) AND wiped in the table (`ck_adr_discussion_tombstone` pins that shape), kind/author/`createdAt` kept; no `state` filter and no count sees it; a write to a deleted
  entry is `404`. Each entry carries the caller's verdicts (`canEdit`: the author, window open; `canDelete`: the author or ADMIN, not yet deleted; `canChangeState`: a live entry with a state and the role above, in any ADR status) so the SPA never re-derives them. The ADR
  carries `canComment` / `canRaiseIssue` (the window as a flag: the composers) and the counts `openIssueCount` (open issues + escalations) and `unansweredQuestionCount` (open questions), tombstones excluded; the list rows carry `openIssueCount`.
  The counts are ONE aggregate per read or list page (`WHERE adr_id IN (...) AND status = 'OPEN' AND NOT marked_as_deleted GROUP BY adr_id, kind`) over the partial index `idx_adr_discussion_open`.
- **Routes.** `GET /adrs/{id}/discussion` (paged; `kind` any-of, `status`; sort `id`, `createdAt`; default **oldest first**), `POST` (201 + `Location`, answers the entry), `GET .../{entryId}`, `PUT .../{entryId}` (edit the body, author only),
  `DELETE .../{entryId}` (204), `PUT .../{entryId}/state` (`{status, resolution?}`: set the target state, idempotent - answered/resolved/reopened; answers the entry). Order of one write (`authorization.md`): the ADR / entry (`404`; an entry of another ADR is
  `404`) → the coarse guard (`403` before the body) → the body (`400`) → under the lock the guard again, then (post and edit only) the window (`409`), then the state against the kind (`400`: a comment has no state, a question is `OPEN`/`ANSWERED`, an issue `OPEN`/`RESOLVED`, a note only with `RESOLVED`).
- **History.** Every post and every REAL state change is an `adr_events` row in the same transaction, params `{entryId, kind}` (never the text; the SPA reads the entry through the discussion endpoint): `COMMENTED`, `QUESTION_ASKED`,
  `ISSUE_RAISED`, `ESCALATED` on a post; `QUESTION_ANSWERED` / `QUESTION_REOPENED`, `ISSUE_RESOLVED` / `ISSUE_REOPENED` (the `kind` param says issue or escalation) on a state change; setting the state an entry already has records nothing. The one exception to "nothing": a RESOLVED entry given a DIFFERENT note keeps its state and has the note replaced (an empty one clears it; who/when follow the editor), still with no history event and audited as `adr.discussion_state_changed` with `from == to`; the same note is a plain no-op.
  **Edits and deletes are NOT events** (decision): the entry itself shows `editedAt` / the tombstone, and the audit trail has `adr.discussion_edited` / `adr.discussion_deleted`; an event per edit would drown the ADR's history in typing.
- **Audit** (`observability.md`): `adr.discussion_posted`, `adr.discussion_edited`, `adr.discussion_deleted` (with `byAdmin`), `adr.discussion_state_changed` (`from`/`to`) after the commit, only on a change; a `403` is the generic `authz.denied`.
- **Body ceilings** (`plugins/Http.kt`): an entry post or edit 64 KiB (`MAX_DISCUSSION_REQUEST_BODY_BYTES`, sized so even a body whose every unit is `\u`-escaped, 60 000 bytes, fits), the state PUT the 16 KiB small ceiling.
- **Web.** The ADR page's Discussion tab (comments and questions) and Issues tab (issues and escalations), `web/CLAUDE.md` "The ADR pages".

## Tags (0.4.0 - built)

Toadie's ADMIN-curated tag categories (`tags/`, V13), trimmed of everything Backstage: a **category** = a name (1-60, single line, unique among active categories
case-insensitively) + an optional description (at most 500) + its **tags** (1-100); a **tag** is in exactly ONE category. `GET /tag-categories` is open to any authenticated user (the
editor's picker, the list filter), every write is ADMIN-only with the guard before the header, the body and the id (`403` even for an unknown id), and the registry is capped at 100 categories. A category carries a `revision` (V13, starts at 1): its **PUT and DELETE take `X-Expected-Revision`** (required: `400` missing; order: guard `403` → header `400` → body `400` → existence `404` → stale revision `409` `revision-conflict` → the claims), judged under the registry lock, so an admin editing a stale copy gets a `409` instead of silently overwriting another admin's tag list; every PUT bumps it (the registry has no no-op rule), a delete bumps it too. The SPA sends the revision the category had when its editor or confirmation OPENED.

- **A tag name** is normalised at every entry (trimmed, control/hidden characters `400`, whitespace runs collapsed, lower-cased), 1-40 characters of letters and digits with spaces and `. _ / + # : -` inside (no comma: events join names with one). It is unique over EVERY row, retired ones included (`uq_tags_name`).
- **Storage.** `tag_categories`, `tags` (one row per tag, `category_id`), `adr_tags` (ADR <-> tag, `persistence.md` "Tag categories (V13)"). Registry writes run in a `lockingTransaction` (a table lock, Toadie's protocol), so two admins editing at once queue; a cross-category claim is `409` naming the owner.
- **Strict.** An ADR write carrying a name that is not a LIVE registry tag is `400` (unknown or retired), a duplicate is `400`, an ADR carries at most 20 (the count is judged BEFORE any name is normalised, so an oversized list is refused without sanitising it).
- **Retired, not erased (the decision).** Removing a tag from a category, or deleting the category (a soft delete that frees its name), RETIRES the tag rows (`marked_as_deleted`). Toadie keeps stored references and reports them as findings; here an ADR keeps its `adr_tags` row and the API serves the tag as `retired: true` (the SPA draws it struck through and says "retired" to assistive technology) until the next tag write
  drops it - and a tag write that still carries it is `400`, so the editor starts from the live tags and says the retired ones are dropped on save. Adding the name to a category again REVIVES the same row, so those ADRs show it live again; moving a tag between categories is two saves (drop, then add). The list's `tag` filter still matches a retired tag on the ADRs that kept it.
- **Seed.** V13 inserts two small categories an ADMIN can rename, extend or delete: **Domain** (`data`, `security`, `infrastructure`, `frontend`, `integration`) and **Scope** (`team`, `system`, `organisation`).
- **Setting them.** `PUT /adrs/{id}/tags` `{tags: [names]}` under `X-Expected-Revision` (a dedicated route, not a field of the document PUT: the document PUT is a content write for Contributors too and tags are the Driver's, Approver's and ADMIN's, in every non-terminal status - `ACTIVE` included, they are outside the content freeze). A wholesale replace applied as a diff; a real change bumps the revision and records one `TAGS_CHANGED` event; the same set is `204` and records nothing.
- **Reading them.** The ADR and every list row carry `tags`. List, export and saved-lens filters use the registry's tag grammar.
  A malformed tag is `400`. The repeatable, any-of `tag` filter allows up to 20 distinct names after canonical normalization.

## Successors (0.4.0 - built)

`adrs.supersedes_id` (V14) on the SUCCESSOR names the ADR it replaces: one predecessor at most, set by `PUT /adrs/{id}/supersedes` `{supersedesId}` (omitted or null removes it) under `X-Expected-Revision`, by the successor's Driver, Approver or ADMIN, **only while the successor is pre-active** (it takes effect at activation; the product assumption that the link also changes once `ACTIVE` was dropped for this reason).

- **Squatting and the detach (decision, `product.md` "Assumptions").** Linking needs no role on the PREDECESSOR, and a predecessor has one successor in play, so a stranger could park a draft on any ADR and block everyone else. The PREDECESSOR's Driver, Approver or ADMIN may therefore **detach** its pending successor: `DELETE /adrs/{id}/successor` (no body; optional `successorId` matches the link under the locks). The SPA sends the successor ID shown when the confirmation opened. Legacy clients may omit it. Under the `ADRLINKS` lock and BOTH rows (id order, the activation's pair order) it clears the successor's `supersedes_id`, **bumps the successor's revision** (its open editors and a racing activation conflict; the predecessor's own revision does not move) and writes `SUCCESSOR_UNLINKED` on both ADRs (audit `adr.successor_detached`). `204`; `403` for anyone else (judged on the predecessor); `409` `adr-frozen` for a terminal predecessor (an activated successor superseded it); `404` when no successor is pending or it differs from the supplied ID. The successor's Driver may link again - detaching is the owner's veto of THIS link, not a ban.

- **The predecessor** must be another live ADR (`400`), `ACTIVE` or pre-active (`400` for a terminal one: nothing left to replace), must not close a cycle (`409`, `SuccessorGraph.cycleClosedBy`, Astrolabe's kernel reduced to a walk UP the stored `supersedes_id` chain from the requested predecessor: O(depth) one-row lookups, never the whole table, and a link whose successor is `CANCELLED`/`WITHDRAWN`/deleted no longer counts; the walk runs under the `ADRLINKS` advisory lock, taken before the row lock, because a cycle spans rows) and must have no other successor in play (`409`; `uq_adrs_supersedes_open` is the partial-unique backstop over non-terminal, non-deleted successors, so a cancelled or withdrawn attempt frees the predecessor for another).
- **Activation.** When the successor becomes `ACTIVE`, the predecessor moves `ACTIVE -> SUPERSEDED` in the SAME transaction: both rows are locked together in id order (the predecessor id is peeked first; every link change bumps the successor's revision, so a link that moved in between is a stale-revision `409` before anything else), the predecessor's revision bumps, and it gets `SUPERSEDED` (actor = the activator) while the successor gets `TRANSITIONED` and `SUCCESSOR_ACTIVATED`. Audit: `adr.transitioned` then `adr.superseded`.
- **Acceptance (1.0.0, checkup C-SEC-1; V19, `product.md` "Assumptions").** Linking is the successor's write, but replacing a decision in force is the Approver's: a successor over an `ACTIVE` predecessor activates only after the PREDECESSOR's Approver (or ADMIN) accepted the link, `POST /adrs/{id}/successor/accept {successorId}` on the predecessor, while that is `ACTIVE`; otherwise the activation is `409` `urn:hammurabi:problem:successor-not-accepted` (ADMIN included: no bypass at activation), judged from the row locked in the activation's transaction right after the stale revision. The acceptance is stored as `adrs.supersedes_accepted_id` (the predecessor accepted for; accepted = equal to `supersedes_id`), belongs to ONE link (a re-point, an unlink or a detach void it; the same link again keeps it; handing the Approver seat on keeps it), bumps no revision and records `SUCCESSOR_ACCEPTED` on both ADRs (the successor's Driver and Approver are told, the actor excepted); it cannot be taken back (detach the successor instead). Links already in effect at the upgrade are backfilled as accepted, pending ones are not (`persistence.md`). A predecessor that is not `ACTIVE` keeps its `400` and a soft-deleted one reads as no link.
- **The predecessor is not `ACTIVE` at that moment** (it was only a draft when linked, or it expired, was cancelled or was withdrawn since): the activation is refused with `400` naming it (a requirement of the move, like the date), and the successor's Driver, Approver or ADMIN removes the link or waits for it to be activated. A predecessor soft-deleted meanwhile reads as no link and the activation goes through, leaving it alone. A pre-active predecessor may be linked precisely so the two can be prepared together; only an `ACTIVE` one is ever superseded.
- **Both ends on the wire.** `supersedes` (the ADR this one replaces) and `supersededBy` (its pending successor, or once `SUPERSEDED` the one that replaced it, even if that one was withdrawn after it took effect; never one cancelled or withdrawn before it activated, and (1.2.0) never a pending one once this ADR itself was cancelled, withdrawn or expired), each `{id, key, name, status}`. History: `SUCCESSOR_LINKED` / `SUCCESSOR_UNLINKED` on the successor (a re-link is both; the old end is resolved even when that ADR was soft-deleted meanwhile, so the unlink is always recorded), and on the predecessor a detach's `SUCCESSOR_UNLINKED`, `SUPERSEDED` and `SUCCESSOR_ACTIVATED` at activation. The detail page shows both links and the "Superseded by ADR-00xx" banner (`web/CLAUDE.md`).
- **The predecessor ends before the successor is in force (1.2.0; the user's decision D3).** A predecessor that is cancelled (pre-active), withdrawn (`IN_REVIEW` or `ACTIVE`) or expired (the sweep) can still have a pending successor, which will now replace nothing (`AdrStatus.endedUnreplaced`: terminal and not `SUPERSEDED`, the ONE rule). In the transaction that ends it: the successor gets a `PREDECESSOR_ENDED` history event (actor = who ended the predecessor, NULL for the sweep) whose notice tells ITS Driver and Approver, the actor excepted ("Notifications"); and the ended ADR **stops listing** the successor everywhere (`supersededBy` null, so no Successor entry, no banner, no `hasSuccessor` match and no export line; `successorInPlayOrInEffect` carries "its predecessor has not ended unreplaced"). The **link stays** on the successor (`supersedes_id` and `supersedes` untouched, its revision does not move): its Driver, Approver or ADMIN removes it with `PUT .../supersedes` and the activation keeps its `400` "unlink it first"; nothing detaches it for them. Only a PENDING successor (pre-active, live) is told: none, a cancelled or withdrawn one, or a soft-deleted one are not; a soft-deleted predecessor records no event and stays untold (a soft delete records none anywhere). A pre-1.2.0 dead link (the predecessor ended before) reads as none and writes no event after the fact. **Locks** (`persistence.md` "Successor links (V14)"): the actor's budget row, the link advisory lock, then the predecessor and the pending successor together by id, so a link written meanwhile either is seen by the ending move or meets a terminal predecessor (`400`), and a racing activation of the successor is a `400` ("unlink it first") or wins and supersedes (the ending is then `409`).

## Search (0.5.0 - built)

`GET /adrs` is the one search surface: the older filters (`status`, `tag`, `participantId` + `participantRole`, `q`) and the 0.5.0 ones, all AND-combined, on ONE predicate for the count and the rows (`AdrListQuery.kt`, `AdrListService.kt`; `list-endpoints.md`).
Plain and full-text ADR pages, export plans and notification pages use read-only `REPEATABLE READ` so their counts and selected rows
share one database snapshot (API-LIST-001).

- **Full-text `text` (decision: a separate parameter from `q`).** `q` stays the cheap name-or-key substring (the key `ADR-0042`, a name fragment); `text` is Adder's full-text search (V15, `persistence.md` "Search and filters (V15)"; `infra/db/Fts.kt`, `SearchBudget.kt`) over ONE stored generated `tsvector` with the accent-folding `hammurabi_search` configuration: the name weighs A, the problem and the decision B, the context, the alternatives and the consequences C. Case- and accent-insensitive ("zolw" finds "Żółw"), no stemming, every word must match (AND, any order), a word of three characters or more matches as a prefix, and no input is a query error: the tsquery is built from `to_tsvector`'s own lexemes (Adder's approach, chosen over `websearch_to_tsquery` so documents and queries share one parser and the operators are plain punctuation). `text` is 2 to 100 code points after trimming with a letter or digit (`400`; blank = no search). The SPA's search box sends `text`; `q` stays in the Filters panel as "Name or key".
- **Ranking.** With `text` the default sort is `-relevance,-number` (`ts_rank_cd`, the weights above, newest among equals); `relevance` is a sortable name only with `text` (`400` otherwise) and any explicit `sort` wins. A search page is at most 20 rows.
- **Snippets, never markup.** With `text` each row carries `match: {name, snippet}` of typed segments `{text, hit}`: the whole name with its hits marked and one or two fragments of the body (decision, problem, context, alternatives, consequences, in that order; empty when only the name matched). `ts_headline` is asked for the page's ids only and returns its input untouched, so it is requested with the control characters U+0002/U+0003 as markers (unforgeable: every name and Markdown field refuses control characters) and split server-side (`splitHeadline`); the SPA renders `text` as React text and wraps the hits in a `<mark>`. Without `text`, `match` is null.
- **The deadline and the cap** (`security.md` "Search"): one `search.timeoutSeconds` deadline for all the statements of a search and at most `search.maxConcurrent` searches at once; the typed `429`s `search-timeout` and `search-busy` carry `Retry-After`. The search term is user content and reaches no log, audit line or span.
- **The other filters.** `createdFrom`/`createdTo` and `updatedFrom`/`updatedTo` are inclusive UTC days (`YYYY-MM-DD`; from after to is `400`); `expiresBefore` keeps the ADRs whose expiry date (the LAST day in force) is strictly earlier, any status, an ADR without a date never matches; `hasOpenIssues` is `openIssueCount > 0` (open issues and escalations) or its complement; `hasPredecessor` is "has a live predecessor", `hasSuccessor` "has a successor in play or in effect, never a cancelled or withdrawn one, nor a pending one whose predecessor ended unreplaced" (the wire's `supersedes` / `supersededBy` objects' rule: one predicate, `successorInPlayOrInEffect`, shared by the ADR read, the list and the export), each `true` or `false`. These four filter names (`participantId`, `participantRole`, `hasPredecessor`, `hasSuccessor`) were `participant`, `role`, `supersedes`, `supersededBy` until 0.9.x: the booleans no longer share a name with the link objects on the ADR, and `role` no longer reads like `GET /users?role=`; V20 rewrote the stored lenses and the SPA still reads the four old URL keys ("Lenses").
- **Not built (assumptions, change on request):** the lens filter has no "me" placeholder (a `participantId` is a user id), a filter has no OR across criteria, and the search does not read the discussion text or the history.

## Lenses (0.5.0 - built)

Saved filters, Toadie's lenses (`lenses/`, V16) ported: a named, per-user snapshot of the list's filters. The payload is the list's OWN filter document (`AdrFilterDocument`: the query parameter names, `status` and `tag` as arrays, the dates as `YYYY-MM-DD`), validated by the SAME rules as the query string (`normalized()`) and stored canonical; it carries no sort and no page (a lens is a filter, not a view). A user keeps at most 50; the name is unique per owner (case-insensitively, `409`). **PRIVATE** = visible to the creator only; **PUBLIC** = visible to every signed-in user (the creator's name beside it), changed by its creator only; an ADMIN may delete a PUBLIC lens (moderation) and sees no PRIVATE one. Existence disclosure and ordering follow Toadie's `mutationVerdict` (`authorization.md`): foreign PRIVATE or unknown = `404`, foreign PUBLIC = `403`, both before the body's `400`. Routes: `GET|POST /lenses`, `GET|PUT|DELETE /lenses/{id}` (PUT is the whole replace: rename, the visibility flip and overwriting the filters; no revision header, the last write wins and the spec says so, like Toadie's; `createdById`/`createdByName`/`createdByDeleted` name the creator). A lens holding a participant or a tag that no longer exists is not an error: it matches nothing until edited. **The stored keys follow the list's names:** V20 (1.0.0) renamed `participant`, `role`, `supersedes` and `supersededBy` inside every stored document (soft-deleted lenses too) to `participantId`, `participantRole`, `hasPredecessor` and `hasSuccessor`; the reader has no alias for the old keys (a pre-V20 document is migrated, not read leniently; `persistence.md` "Lens filter names (V20)"). A `status` or `participantRole` value this release no longer knows (a later release removed it) is dropped when the lens is read, an unknown key is ignored, and the lens is listable all the same (it matches on its remaining keys until it is saved again; `persistence.md` "Persisted enums"). The 50-lens cap is counted under a per-user advisory lock, so racing creates cannot overshoot it. Applying a lens is the ordinary list request with its filters; the SPA's picker copies them into the URL (`web/CLAUDE.md`).

## Notifications (0.6.0 - built)

Adder's `notifications/` ported and reshaped from chat to ADRs (V17, V18; `persistence.md` "Notifications", `security.md` "Notices"). The bell, a per-user set of switches and an email digest tell a DACI participant what happened to an ADR they take part in.

**Every notice derives from a history event.** `AdrEventService.record` offers each event to `AdrNotices` (an `adrs/` interface the `notifications/` package implements; the composition root wires it) right after the event row, in the write's own transaction: a notice commits or rolls back with its change, and a refused or no-op write (which records no event) makes none. The pure `noticeFor` (`NotificationPlan.kt`) maps event to notice (the events of one write on one ADR are offered together and made by one insert, `persistence.md` "Notifications"); **the actor is always taken out of the audience** (nobody is told of their own write; a system event has no actor).

| Type | Made by | Reaches | `detail` / second ADR |
|---|---|---|---|
| `ROLE_ASSIGNED` | `PARTICIPANT_ADDED` (creation included), `PARTICIPANT_CHANGED` | the person given the role (a Driver handover tells everyone whose role changed, the actor excepted) | the new role |
| `ROLE_REMOVED` | `PARTICIPANT_REMOVED` | the person removed | the role they held |
| `STATUS_CHANGED` | `TRANSITIONED` | every participant, Informed included | the new status, or `SENT_BACK` for an in-review ADR returned to draft (the same target is also a forward step from `PROBLEM_RAISED`, so the pair decides; the web and the mail say "sent back to draft"); a withdrawal is the plain word `WITHDRAWN`; **never the reason** (free text, history only) |
| `DISCUSSION_POSTED` | `COMMENTED`, `QUESTION_ASKED` / `ISSUE_RAISED`, `ESCALATED` | Driver, Approver and Contributors / Driver and Approver | the entry kind |
| `DISCUSSION_SETTLED` | `QUESTION_ANSWERED`, `ISSUE_RESOLVED` (an escalation too) | the entry's author | the kind (a question was answered, an issue or escalation resolved) |
| `ADR_EXPIRED` | `EXPIRED` (the sweep, no actor) | every participant | the expiry date |
| `ADR_SUPERSEDED` | `SUPERSEDED` (the successor's activation) | every participant of the predecessor, the activator excepted | second ADR = the successor |
| `SUCCESSOR_LINKED`, `SUCCESSOR_UNLINKED` | the successor-side `SUCCESSOR_LINKED` / `SUCCESSOR_UNLINKED` (a link, a re-link, a drop, a detach) | the PREDECESSOR's Driver and Approver; the notice is about the predecessor (a link reads as a PROPOSAL from 1.0.0) | second ADR = the successor |
| `SUCCESSOR_ACCEPTED` (1.0.0) | the successor-side `SUCCESSOR_ACCEPTED` (the predecessor's Approver or ADMIN accepted) | the SUCCESSOR's Driver and Approver, the actor excepted; the notice is about the successor; the predecessor-side mirror event makes none | second ADR = the predecessor |
| `PREDECESSOR_ENDED` (1.2.0) | the successor-side `PREDECESSOR_ENDED` (the ADR a pending successor was set to replace was cancelled, withdrawn or expired) | the SUCCESSOR's Driver and Approver, the actor excepted (none for the sweep); the notice is about the successor | second ADR = the predecessor that ended, `detail` = its new status (`CANCELLED`, `WITHDRAWN`, `EXPIRED`) |
| `EXPIRY_REMINDER` | the reminder pass (no event) | Driver and Approver | the expiry date |
| `EXPIRY_CHANGED` (1.0.0) | an `UPDATED` event whose `changed` lists `expiresOn`, while the ADR is `ACTIVE` (a draft's date notifies nobody; the status is judged in the same statement that finds the audience) | every participant, Informed included, the actor excepted | the new date; none = the date was removed |

A reopen, an edit and a delete of an entry notify nobody (as they record no ordinary event). The detach's mirror event on the predecessor (`SUCCESSOR_UNLINKED {successorId}`) makes no second notice. A deleted account is never notified; a switched-off kind is not made for the person (below).

**The row is a pointer** (`notifications`): recipient, type, actor (null = the system), the ADR, an optional second ADR and one short `detail`; the actor's name and the ADR's key and name are read when a page is read, so a rename shows at once. Hard-deleted with the ADR or user and by retention (`notifications.retentionDays`, 90).

**Routes** (all on the per-user `read-state` bucket, 240/min): `GET /notifications` (the caller's own, newest first, `seen` filter, sort `id` / `createdAt`, `total` capped at 1000, a soft-deleted ADR's notices hidden), `POST /notifications/{id}/seen` (`204`; another person's, an unknown or a hidden one (of a soft-deleted ADR or a kind this build does not know) is the same `404`), `POST /notifications/seen-all` (`204`), `GET` / `PUT /users/{id}/notification-preferences` (self or ADMIN). No audit line for the seen writes (view state); the PUT audits `user.notification_preferences_changed` on a real change.

**Preferences** (Adder's V5-style disabled set, wholesale replace; the table stores the DISABLED `(kind, channel)` pairs, the wire speaks kinds): the GET answers `kinds` (`{type, inApp, email}` per kind) and the PUT takes the SAME `kinds` back (1.0.0; it was a list of disabled pairs), so a round trip changes nothing and writes no audit line. A kind left out of a PUT is on, one listed twice (or a list longer than the kinds) is `400`, and the last write wins (no revision). Per kind, two channels. `IN_APP` off = no notice is made for the person from then on (existing ones stay); `EMAIL` off = the digest never mails the kind (the bell is unchanged). Everything is on for a new user and a new kind. `emailAvailable` is false without a mailer (then the email switches do nothing).

**The email digest** (`NotificationDigest.kt`, `NotificationEmail.kt`; `security.md` "Notices"): a notice still unseen after `notifications.email.delaySeconds` (300) is mailed in ONE plain-text email per person per `notifications.email.minIntervalSeconds` (900), in the recipient's stored language (EN/PL), naming who, what and the ADR KEY with an ADR link built from `mail.appUrl` (expiry reminders point to `/adrs/{id}#validity`); never an ADR name or text (a notice whose second ADR was since soft-deleted is not mailed, like one whose own ADR was; the bell shows its key as a dash). It uses the existing mailer (`MAIL_TRANSPORT`); with none the digest idles and the bell keeps working. `notifications.sweepEnabled` (the suite sets it false), `sweepIntervalSeconds` (60).

**The expiry reminder** (`ExpiryReminders.kt`; Covenant's `ReleaseLineReminders` shape): `adrs.expiry.reminderDays` (default 14, `0` disables, 0..365). Each hourly housekeeping of the notification sweep (and its first tick) finds `ACTIVE` ADRs whose expiry date is today up to N days ahead and, per ADR in its own transaction under the row lock, stamps `adr_expiry_reminders` (one row per ADR holding the date reminded for; the upsert only fires when it differs) and makes the `EXPIRY_REMINDER` notices for the Driver and the Approver. So it is sent **once per ADR per expiry date; a changed date re-arms it, but at most once per ADR per UTC day** (the marker holds only the last date, so without the day gate an Approver toggling the date A, B, A would re-arm it at every pass; a date changed again the day of the last reminder is reminded the next day, so a date moved to TODAY on the day of the last reminder is not reminded again: the `EXPIRY_CHANGED` notice and the `ADR_EXPIRED` notice still inform); its notices are charged to the ADR's Approver's mail budget ("Notifications" decision 4); audit `adr.expiry_reminded`. An ADR whose date is set inside the window is reminded at the next pass. Decision: the pass lives in the notification sweep, not the expiry sweep's loop, because it makes notices and shares that sweep's mail cadence; `AdrExpirySweepTest`'s config stays untouched.

**Decisions and assumptions (change on request):** (1) the digest cadence is the deployment's (`delaySeconds` / `minIntervalSeconds`), not a per-user frequency; "email off" is every EMAIL switch off. (2) A comment reaches the Driver, Approver and Contributors but an issue or escalation only the Driver and Approver. (3) STATUS_CHANGED is for user-made transitions; an expiry and a supersede have their own types instead of a second STATUS_CHANGED. (4) Adder's per-actor digest budget is ported as a counter of NOTICES (1.2.0, V21, C-SEC-4; the user's decision): the first 200 notices an actor's writes make in a UTC day (`notifications.email.maxNoticesPerActorPerDay`; every notice made counts, including a kind its recipient switched off) stay eligible for the email, later ones keep their bell notice and are never mailed (not delayed, no summary); an ADMIN actor is not exempt; a notice the SYSTEM makes (the expiry sweep's, the reminders') is charged to the ADR's current Approver, the person who decides when a decision in force ends, and is exempt only when the ADR has no active Approver; a role audience is admitted Driver, Approver, Contributors, Informed first (`security.md` "Notices" (5)). (5) The detach tells the predecessor's other lead only; the successor's Driver is not told that a link was detached (the spec names the predecessor's Driver and Approver). (6) The web polls the unseen count once a minute (Hammurabi has no live channel).

## Export (0.8.0 - built)

`adrs/AdrMarkdown.kt` (pure), `AdrStatusWords.kt` (the status words, EN/PL, shared with the notification email), `AdrExportService.kt`, `AdrExportRoutes.kt`, `AdrExportArchive.kt` (the ZIP streaming). Two reads, **open to every authenticated user** (every ADR is readable; a missing or soft-deleted one is `404`), behind the per-user `export` bucket (20/min, `security.md`), audited as `adr.exported` / `adr.exported_bulk` (ids and counts only, `observability.md`).

- **One ADR.** `GET /adrs/{id}/export` answers `text/markdown; charset=utf-8` with `Content-Disposition: attachment; filename="ADR-0042-<slug>.md"`. The slug (`adrSlug`) folds diacritics (NFD, plus `ł ø đ ß æ œ` which do not decompose), lower-cases, turns every run outside `[a-z0-9]` into one `-`, trims dashes and cuts at 60 characters; a name with no Latin letter or digit gives no slug (`ADR-0042.md`). So the header is always plain ASCII: no `filename*` (no sibling sends one; Covenant's version download likewise names its file by a slug). The slug is also the target of the links between exported files.
- **The document** follows adr-tools: `# 42. <name>`, `Date: YYYY-MM-DD`, `## Status`, `## Context`, `## Decision`, `## Consequences`, then Hammurabi's `## Alternatives considered` (left out when blank), `## Roles (DACI)` (Driver, Approver, Contributors, Informed by display name; absent roles left out) and `## Tags` (`- Category: tag`, a retired tag marked), and a footer `<!-- Exported from Hammurabi on <date> -->` (the date only: no user, no version, so nothing personal). **Decisions (change on request):** `Date` is the day (UTC) the ADR first became `ACTIVE` (the first `TRANSITIONED` event into it), else the day it was created; `## Status` is the status in words, then a line `Expires on <date> (the last day the decision is in force)` when set, `Supersedes [ADR-0007: Name](ADR-0007-slug.md)`, and `Superseded by [...]` once `SUPERSEDED` (a successor still pending reads `To be superseded by` once accepted and `Successor proposed:` before, so the file never claims a supersession that has not happened; an ADR that was cancelled, withdrawn or expired names no pending successor at all, 1.2.0); `## Context` holds the problem as `### Problem` and, when there is one, the context as `### Background`; an empty required section (`## Decision`, `## Consequences` of a draft) keeps its heading with `_Not recorded yet._`; the document is English whatever the exporter's language (a hand-off file, adr-tools' headings are English). The Markdown fields are **verbatim** (CRLF and CR to LF, the blank lines around a field dropped, nothing escaped: it is a `.md` file we never render); only a link's text is escaped (a `]` in a name), and names elsewhere are written as they are.
- **Bulk.** `GET /adrs/export?<the list's filters>` answers `application/zip` (`adr-export-YYYY-MM-DD.zip`): `ADR-NNNN-slug.md` per matching ADR and a last entry `index.md` (the adr-tools `toc` shape, `- [ADR-0001: Name](file.md) (Active)` in number order, built from what was actually written, so an ADR deleted meanwhile is skipped in both). It reads the list's filters with the list's parser and `AdrFilterDocument.normalized()` (same names, same `400`s), **`text` allowed** (it runs under the search's deadline and cap like the list, so the `429`s `search-timeout` / `search-busy` apply) and no `page`, `pageSize` or `sort` (number order). **Cap 500** (`adrs.export.maxAdrs`, env `ADRS_EXPORT_MAX_ADRS`): a match over it is `400` naming the total ("narrow the filters"), never a truncation; a match of none is a `200` holding only `index.md`. Everything refusable (the filters, the deadline, the cap) is judged by `AdrListService.exportPlan` BEFORE the first byte; the archive is then streamed with `java.util.zip` 25 ADRs per transaction (`AdrExportService.documents`), so memory holds one batch, never the 500; a failure after the first byte ABORTS the connection (the writer cancels the channel with the cause and never finishes the zip: a client sees a failed download, never a complete-looking archive with files missing; `AdrExportStreamTest` pins it). At most `adrs.export.maxConcurrent` (2) bulk exports stream per process, the next is `429` `export-busy` (`security.md`); `HEAD` is `405`. The slug folds with NFKD (fullwidth letters and ligatures too) plus `ß ẞ ł ø đ æ œ`. `Compression` is told to skip `application/zip`.
- **Web.** Export Markdown on the ADR page, Export (ZIP) on the list over its current filters (`web/CLAUDE.md` "The ADR pages"). **Not built (assumptions):** no import, no per-language export, no `docs/adr` repository layout (the files sit flat in the archive), no format switch (adr-tools' Markdown only).

## Overview (0.9.0 - built)

`adrs/AdrOverview.kt` (the wire types and the caps), `AdrOverviewService.kt`, `AdrOverviewRoutes.kt`; the page is `/decision-log` ("Decision log", `web/CLAUDE.md` "The ADR pages"). **`GET /adrs/overview`** is a read open to **every authenticated user** (every ADR is readable), with no parameters, no audit line and **no rate bucket** (like `GET /adrs`: the answer is capped in every section, comes from a constant number of indexed statements and is one call per page load). It is the second purpose-built document outside the paged envelope (`list-endpoints.md` points here): no parameters, a document `{counts, inForce, recentlyDecided, expiringSoon, awaitingDecision}` whose list sections are `{total, items, more}` (`more` = `total - items.size`, never negative), every one capped as below, built from a constant number of statements in one transaction; its "+N more" links are the list's own filters.

| Section | What it holds | Cap (`more` = what is left) |
|---|---|---|
| `counts` | every status in lifecycle order, zero included (live ADRs) | none (eight) |
| `inForce` | `total` = the ACTIVE ADRs; `categories` -> tags -> ADRs, an ADR under EACH of its live tags, newest number first; `untagged` | 20 per tag and for `untagged`; at most 100 tag groups (category name, then tag name, case-insensitive), the tags beyond counted in `hiddenTags` |
| `recentlyDecided` | the ACTIVE ADRs that became active most recently | 10 |
| `expiringSoon` | ACTIVE ADRs whose `expiresOn` is on or before today + `days` (UTC), soonest first, number ascending among equals | 20; `days` = `adrs.overview.expiringSoonDays` (30, 1..365) |
| `awaitingDecision` | ADRs `IN_REVIEW`, the longest wait first, each with its `approver` and `mine`; `mineTotal` counts ALL the caller's | 20 |

**Decisions (change on request).** (1) *Time from the row, not a history scan:* an ACTIVE ADR cannot have left that status, so `status_changed_at` IS its activation (the same stamp as its `TRANSITIONED` event), and for an ADR in review it is when it was submitted (again after a send back); no event is read and no migration was needed (the status, expiry and tag indexes of V10-V15 serve every statement). (2) *"Recently decided" lists ADRs still ACTIVE;* one since withdrawn, expired or superseded is gone from it (the decision is no longer in force). (3) *A retired tag does not group an ADR:* "live tags" only, so an ADR whose only tags were retired reads as untagged; a category or tag with no ACTIVE ADR is absent. (4) *No lower bound on the expiry horizon:* a date already past that the sweep has not acted on (or a deployment with the sweep off) is the most urgent entry, so it leads the list; the web marks it "Overdue". (5) *The caller's own queue is a count plus a flag, not a second list:* `mine` marks the rows, `mineTotal` covers the ones beyond the cap, and the page links the list filtered `status=IN_REVIEW&mine=1&participantRole=APPROVER`. (6) The statements run in ONE read-only REPEATABLE READ transaction (one snapshot, so a total and its rows always agree; `more` is still clamped at zero): the status counts; the awaiting page, its Approvers (`AdrParticipantService.leadsOf`, then `activeAmong`: a soft-deleted Approver reads as `approver: null`, "no Approver", so the gap surfaces) and the caller's count; the recent and the expiring page and count; the per-tag groups in ONE windowed statement (`count`, `row_number` and `dense_rank` `OVER`, a raw statement because Exposed has no spelling for it, every argument bound); the untagged count and page. Rows carry no Markdown, no participants other than the awaiting Approver and no tags.
(7) *The untagged group has no filtered list:* the ADR list has no "untagged" filter, so the group's "more" link can only open the active ADRs (`status=ACTIVE`), reworded "All active ADRs" in the web because its target is larger than the group. (8) "Today" and the horizon belong to `AdrOverviewService` (an injected `Clock`, the UTC date; the horizon is read and boot-validated by the composition root), and the tag-group cap is a constructor argument (default 100) so a test can make the hidden count deterministic in the shared database; the web derives "overdue" from the response's `generatedAt`, not the browser clock.
**Web.** Count strip (each status badge links the list in that status), Awaiting decision (the caller's rows tinted grape, badged "Needs your decision", counted above the list), Expiring soon, Recently decided, In force by tag; rows open their ADR and Expiring soon opens its Validity section. Every "+N more" opens the list's own filters (`status=ACTIVE&tag=...`, `status=ACTIVE&expiresBefore=<horizon+1>`). **Not built (assumptions):** no per-team or per-participant slice of the log, no history/chart of decisions over time, no "mine" lens on the other sections.

## My work

`GET /adrs/my-work` returns a snapshot of the caller's current DACI assignments, optionally narrowed by `participantRole`. The API excludes soft-deleted ADRs and scopes every section to the authenticated user, including an ADMIN. It returns `generatedAt` and four sections with up to 12 `items` each. `hasMore` indicates that the cap trimmed the section.

- **Needs your action** includes reviews awaiting the Approver, active expiry for the Approver, returned or stalled drafts for the Driver, and active open escalations for the Driver and Approver. **Worth watching** shows attention signals for the other roles. An ADR appears at most once across the two sections, with an actionable reason taking precedence over a watch reason.
- Draft inactivity starts at the latest substantive document edit or lifecycle move, with a 14-day threshold. A review waiting at least seven days displays its age from the latest submission. Tag changes and routine comments leave the draft clock alone. Active expiry uses the `adrs.expiry.reminderDays` window, including overdue decisions until the sweep closes them. Setting the window to `0` hides expiry attention.
- **Recent activity** includes the last seven days of document and expiry edits, lifecycle moves, discussion events and successor activity, newest first. It can include a recently completed ADR while the viewer still holds a role. Tag and participant changes are available in the full History. **My ADRs** shows nonterminal ADRs ordered by their last meaningful event, with a link to the full ADR list filtered to the caller and selected role.

Rows link to the ADR workflow, Validity, or the relevant discussion tab. The page derives its queue from current state and history at read time. Changes to an ADR clear the corresponding item when its rule no longer applies.
